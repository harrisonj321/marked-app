## SHOULD overrides (locally documented)

None currently documented.

**Icon convention note (not an override):** this app's general-purpose icons (`src/components/icons.tsx`) are inlined SVG rather than imported from the `lucide-react` package. A previous revision of this file recorded that as a SHOULD override; it wasn't one, and the entry is removed rather than carried forward. `STANDARD.md` §6's MUST is "use Lucide as the default general-purpose icon language," not "depend on the `lucide-react` npm package specifically," and `reference/audit-matrix.md`'s own canonical row names Marked.'s approach directly: "vendored as hand-copied inline SVGs (no npm dependency) matching Lucide's default style exactly" is listed alongside Noted.'s and Tacos' `lucide-react` imports as part of the same "cleanest convergence in the entire audit." The file's own header states these are Lucide's own path data, embedded directly to avoid the dependency, and spot-checking several against the current `lucide-react@1.34.0` release confirms this -- `X`, `ChevronDown`, and `Plus` are byte-for-byte identical, and `Calendar` differs by a 1px revision Lucide itself made upstream after this copy was taken. Nothing here needs revisiting unless a future icon is added that Lucide provides and this file doesn't already have inlined -- at which point the new glyph is added the same way, not a reason to switch the existing ones to a live import.

## Phase 4.1: shared-package adoption status

Adopted `@maker428/ui@0.1.1` (pinned exact) per `reference/migration-roadmap.md` §4.1:

- **Theme tokens, glow/shine/halo, elevation, safe-area raw insets** -- `src/index.css`'s duplicated `:root` declarations for these were removed in favor of `@maker428/ui/styles.css` (imported once, in `main.tsx`); the values were already byte-identical, so this was source consolidation, not a redesign. What's left locally is genuinely Marked.-specific: the paper-grain texture and the ledger color palette, plus the safe-area *composite* formulas this app builds on top of the package's raw `--safe-area-*` tokens (those composites don't match the package's own `--mobile-*-gap` shortcuts, so they stay local rather than being force-fit).
- **The one remaining direct glow bypass** named in `reference/audit-matrix.md` -- `.onboarding-dot-active`'s hand-written `box-shadow` -- now goes through the canonical `--object-glow` recipe instead.
- **`IconButton`** -- adopted at all eight icon-only controls in the app (calendar open, all four sheet close buttons, the ledger-row manage/edit button, the settings default-state swap, and the orientation demo's calendar button). The app's own icon glyphs are passed through unchanged as `children` (see the icon-convention note above for why they're inlined SVG rather than `lucide-react` imports -- both are compliant); two controls whose glyph has always rendered smaller than the primitive's 20px default (the manage icon at 16px, the swap icon at 18px) get a small unlayered CSS override preserving that exact size.
- **`MakerMark`** -- the footer attribution is now `<MakerMark version={__APP_VERSION__} />` rather than a hand-typed string carrying the same canonical wording.
- **The shared overlay-accessibility helper (`useOverlay`)** -- closes the tour focus-trap gap; see below.
- **`Sheet`** -- deliberately not adopted. This app's four native `<dialog>` sheets remain valid per `STANDARD.md` §10.1 for content this simple, exactly as the roadmap anticipated; nothing about this migration required touching them.

Also closed in this same phase, independent of the package (`STANDARD.md` §15, `patterns/pwa-and-installation.md` §2.2): the PWA manifest's missing maskable icon pair. `icon-512.png` previously carried both `purpose: 'any'` and `purpose: 'maskable'` at once -- the exact anti-pattern §2.2 names, since an `any` icon is authored trusting nothing will crop it. The manifest now declares a genuinely separate, generously-padded `icon-192-maskable.png` / `icon-512-maskable.png` pair (same mark and background, rescaled inward so it survives an arbitrary adaptive-icon crop), matching Tacos' canonical four-icon reference.

### Onboarding-tour accessibility gap: closed

The hand-rolled onboarding-tour overlay (`src/components/OnboardingTour.tsx`) wraps its rendered content in one container, portals it straight to `document.body`, and calls the shared `useOverlay` on it, providing the full contract: focus entry, full Tab/Shift+Tab trapping (the originally-named gap -- previously nothing stopped Tab from leaving the tour into the screen underneath), topmost Escape ownership (replacing a manual `window` keydown listener), scroll locking (replacing a manual `document.body.style.overflow` toggle), focus return to whatever opened the tour on close (previously absent entirely -- a genuine new correctness win, not a preserved behavior), and real background isolation (`isolateBackground` at its default `true`, unset locally).

Background isolation was initially adopted incompletely: the tour was left nested inside the app tree with `isolateBackground: false`, and `Home.tsx`/`OnboardingOrientation.tsx` hand-marked only their own `<main>` inert to compensate. That missed any *other* interactive content mounted at the React root alongside them -- concretely, `UpdatePrompt` (`main.tsx` renders it as a sibling of `<App/>`, not inside it), which stayed reachable and screen-reader-visible while the tour was open. Portalling the tour to `document.body` and using the package's own isolation (rather than a local substitute) closes this fully: isolation now applies to the whole React-root branch the package can see, not just whichever single sibling was hand-wired, so it reaches `UpdatePrompt` the same way it reaches Home/the demo shell, without either needing to know the tour exists. The previous per-screen `inert` toggle is removed as no longer needed.

`0.1.0`'s own opener-capture defect (this app was the first real consumer to hit it: a child effect could move focus before the package's registration effect ran, silently capturing the tour's own about-to-unmount element as "opener") is fixed centrally in `0.1.1` -- the capture now happens at render time, before any descendant effect can run. The local `returnFocusTo` render-time-capture workaround this app carried to compensate is removed; `useOverlay`'s own default capture is used as-is.

Verified with tests (`OnboardingTour.test.tsx`): Tab wraps last-to-first and Shift+Tab wraps first-to-last within the tour, including with reachable-looking siblings present in the DOM (jsdom doesn't enforce `inert`, so this proves the trap itself, not just the attribute); focus returns to a real external opener once the tour closes, with no local capture involved; Escape (fixed to dispatch from the actually-focused element, matching real browser event bubbling -- `fireEvent.keyDown(window, …)` never reached `document.documentElement` at all) still exits the tour as skipped, and is still ignored during the staged finale's closing beat; background isolation reaches every sibling outside the tour -- both Home's own content and a rendered stand-in for `UpdatePrompt` -- and is fully released on close.

## Phase 6.1: responsive, viewport, and orientation compliance

Audited against `STANDARD.md` §24, `patterns/responsive-and-viewport.md`, and `reference/viewport-test-matrix.md` (v1.1.0). Verified live (not only by inspection) against the matrix's representative sizes -- narrow/large phone in both orientations, a landscape-constrained phone (740×360), tablet portrait/landscape, a reduced-width split-screen pane (500×1000), and desktop (1200×800 / 1440×900) -- plus live rotation, live resize across the app's breakpoint, and a simulated on-screen-keyboard height reduction. Real sign-in/ledger/settings flows were exercised against the Firebase Emulator Suite for this (`VITE_FIREBASE_EMULATORS=1`) rather than the production project, so this generated no real user data.

**Found and fixed** -- a genuine, reproducible failure, not a hypothetical: on a short/landscape-constrained viewport (a landscape phone; a foldable's cover or unfolded-wide state would hit the same thing), the pre-auth orientation's demo shell -- and, less commonly, the "Tour Marked." replay over the real Home -- could leave a coach step's real target (most visibly `open-settings`, anchored to the footer) partially or fully below the fold. The screen underneath a modal tour is both scroll-locked (`useOverlay`'s own body lock) and `inert`, so once that happened there was no gesture left that could bring the target back into view; the coach callout's own placement also had no vertical clamp the way its horizontal placement already did, so it could independently render off the top or bottom edge on the same short viewports. Confirmed with `getBoundingClientRect()`, not just visually: at 740×360, the `open-settings` target sat 30px past the bottom edge before this fix.

Fixed with three small, targeted changes -- no product, visual, or navigation redesign:
- `.screen` (`src/index.css`) now caps at the viewport height (`height: 100dvh`, was `min-height`) and scrolls internally (`overflow-y: auto`) once its content genuinely exceeds that, so a screen has something to scroll on its own regardless of whether `document.body`'s own scroll is locked by a modal overlay.
- `useTourTargetRect` (`src/hooks/useTourTargetRect.ts`) scrolls a newly-active step's target into view (`scrollIntoView({ block: 'center' })`, instant, not smooth) as part of establishing where the spotlight belongs. This is what actually reaches the target now that `.screen` has something to scroll, and it works despite `inert` because it's script-driven, not a user gesture. Deliberately does *not* force an extra `getBoundingClientRect()` read alongside the scroll -- that would reintroduce exactly the mid-transform race the hook's existing `skippedInitialReport` handling already guards against (verified: two existing tests for that guard failed when an unconditional re-measure was tried, and pass with the scroll-only approach). The existing capture-phase `scroll` listener already turns a genuine scroll into a `remeasure()`.
- `OnboardingTour` (`src/components/OnboardingTour.tsx`) gives the coach callout a vertical clamp (`CALLOUT_MAX_HEIGHT_PX`), mirroring the horizontal clamp it already had, so it can't render off the top/bottom edge regardless of viewport height or a step's body-text length.

Verified live after the fix: both the DemoShell (pre-auth) and the real-Home "Tour Marked." replay paths, at 740×360, with the previously-cut-off `open-settings` target and its callout both fully within the viewport; a live portrait↔landscape rotation mid-step re-positions the spotlight/callout correctly with no reload and no lost step. Full existing suite (563 tests), typecheck, lint, and production build all pass unchanged in shape (only the two tests exercising the changed hook needed the approach above, not a changed expectation).

**Evaluated and intentionally left unchanged:** `.screen`'s fixed `max-width: 26rem` centered column, which reads as a wide, mostly-empty margin on a tablet or desktop viewport. This is the "mobile-width-locked... with desktop refinements" pattern `STANDARD.md` §12 already names as the family default, not a compliance gap -- `patterns/responsive-and-viewport.md` §5 reaches the same conclusion directly ("a single column that grows its max-width... is often the right answer through the entire phone-to-desktop range"). Widening it would be a visual-identity change outside a compatibility pass. Every dialog (`.day-detail`, `.settings-sheet`, `.calendar-sheet`, `.ledger-sheet`) already renders as an ordinary centered, content-sized dialog at every width tested, which is correct desktop dialog behavior on its own terms.

Also confirmed correct, not changed: native `<dialog>`'s own `:modal` UA stylesheet (`max-height: calc(100% - 6px)`, `overflow-y: auto`) already caps and internally scrolls every sheet on a short viewport -- checked directly against this app's own computed style in a real browser, not assumed from the spec -- so none of the four needed an explicit `max-height`; `.calendar-sheet`'s own explicit `dvh`-based cap was already correct. The same native behavior already keeps a focused field visible as the viewport shrinks (verified: Settings' Name field stayed visible with the viewport shrunk to 200px tall), so no on-screen-keyboard-specific handling was needed either.

**Ready to adopt, not yet possible:** `@maker428/ui@0.3.0` adds `useMediaQuery`/`useIsCompactViewport` and a `--mobile-left-gap`/`--mobile-right-gap` safe-area pair (`STANDARD.md` §24.4, §24.6). The left/right pair is a direct generalization of this app's own `calc(var(--space-3) + var(--safe-area-{left,right}))`, cited as the evidence for adding it centrally -- unlike the existing top/bottom `--mobile-*-gap` pair (Phase 4.1, above), which didn't match this app's own composite formula closely enough to adopt, the left/right pair is modeled on this app's exact arithmetic and would be a clean, direct swap at its four call sites (`.screen`, `.onboarding-topbar`, `.onboarding-intro`, `.onboarding-install`) once available. Not done now: `0.3.0` is prepared but not yet published to the public npm registry (only `0.2.1` currently is), and installing it via a local-path/tarball reference would leave a dependency a clean `npm install` in Vercel's deploy environment can't resolve (the same npm-registry reasoning `reference/shared-package-architecture.md` §7 already gives for this family). This app has no live-breakpoint JS to migrate onto `useMediaQuery`/`useIsCompactViewport` today, since its one layout breakpoint (`max-width: 480px`) is CSS-only.

## Phase 6.2: wide/short landscape composition

Follow-up to Phase 6.1 after visual review: the previous pass made the wide/short shape (a landscape phone, an open foldable, a landscape tablet) *functionally* correct -- nothing clipped, nothing unreachable -- but left it visually unrecomposed, a portrait single-column stack simply re-centered in a wider box. That's a real, distinct finding from the "leave `.screen`'s 26rem cap alone at tablet/desktop widths" conclusion Phase 6.1 already recorded above: that conclusion covers the *portrait-shaped* wide case (a tall tablet, an ordinary desktop window), where the existing centered column is genuinely the right call per `STANDARD.md` §12. It says nothing about the *landscape-shaped* wide case, which is what this phase addresses -- the two are not in tension.

**The condition, and why it's shaped this way:** `@media (min-width: 640px) and (min-aspect-ratio: 1/1)` in `src/index.css`, scoped to `.home-main:has(.tracker-title)` for the recomposition itself and to `.screen` for the width/spacing changes. Width alone can't distinguish this case (a foldable's *portrait* cover screen and a tablet's *portrait* orientation both comfortably exceed 640px too), and `orientation: landscape` was ruled out per `patterns/responsive-and-viewport.md` §6.2 (it can misfire on a resized window with no physical orientation at all). `min-aspect-ratio: 1/1` is what actually distinguishes "wider than tall" live, regardless of whether a rotation, a window resize, or a fold produced it -- verified directly against the matrix: it fires for every landscape-shaped row (740×360, 930×430, 850×380, 880×720, 1200×800) and correctly does *not* fire for the foldable's own open-*portrait* state (720×880, aspect 0.82), even though its width alone clears 640px.

**The recomposition:** `.screen`'s max-width grows from 26rem to 42rem in this state only (still capped, still centered, never edge-to-edge or full-bleed), and `.home-main`'s three existing children -- `.today-date`, `.tracker-title`, and `TodaySection`'s `.today` -- move from a single vertical stack into a two-column arrangement (date over title on the left, the toggle/status/note-link column on the right), via CSS Grid `grid-template-columns`/named row placement on the *existing* elements. No JSX changed: the grid reaches `.today-date` and `.tracker-title` by selector, so Home.tsx's markup is untouched, and the guest sign-in and empty-account states (which render different children under the same `.home-main` class) are excluded by the `:has(.tracker-title)` scope and keep their plain centered stack exactly as before. This is one ledger's single control read left-to-right instead of top-to-bottom, not a dashboard of independent panels -- no new surface, no new panel chrome, nothing that isn't already on the portrait screen. `.screen`'s own vertical `gap` and padding also tighten in this state, closing the "overly loose vertical spacing" the visual review named specifically. Degrades gracefully with no `@supports` needed, the same way `.ledger-row:has(…)` already does elsewhere in this file: a browser without `:has()` keeps the (still fully correct, Phase 6.1-verified) portrait-style stack in landscape too.

**Verified visually** at every landscape-shaped matrix row (740×360, 930×430, 850×380, 880×720, 1200×800) against portrait counterparts (360×740, 430×930, 720×880 foldable-open-portrait, 800×1200 tablet-portrait) to confirm portrait is byte-for-byte unchanged; live rotation in both directions (with a dialog open, and mid-onboarding-tour) re-composes instantly with no reload and no lost state, since the whole mechanism is a live media query with no JS driving it (`patterns/responsive-and-viewport.md` §4.2's "prefer plain CSS wherever a viewport condition only changes styling"). The onboarding tour's coach spotlight/callout (Phase 6.1's fix) needed no further change -- `useTourTargetRect` measures the real, current position of whichever element the current step targets, so it followed the toggle and title to their new grid cells correctly without modification.

**The standard-level lesson applied here, learned from `reference/viewport-test-matrix.md` §2.1's own account of a defect in a sibling app:** a wide landscape row is not evidence of zero safe-area, and this phase's own new two-column composition is exactly the shape §2.1 warns about (a layout that starts using extra width once a breakpoint-like condition is crossed). Verified with `--safe-area-left`/`--safe-area-right` forced non-zero (44px), independently on each side and then both together, at 930×430: `.screen`'s own existing `padding-left`/`padding-right` formula (unchanged by this phase -- only `max-width`, `gap`, and vertical padding were touched) already keeps both the identity column and the control column clear of the simulated inset on whichever edge it's forced to, with no horizontal overflow (`scrollWidth === clientWidth`) when both are forced at once. This app didn't repeat Noted.'s gap because the new layout was built *inside* `.screen`'s existing safe-padded box rather than introducing a second edge-owning surface of its own -- worth stating plainly since that was a matter of how this composition happened to be built, not a check that would have caught a different structural choice.
